# E2B token accounting and output limits

Verified on 2026-09-19 local time against the active `gemma4-e2b` API, llama.cpp `b10909-a2878d30d`. No server or harness defaults changed.

## Input accounting

The saved thinking-off request has 368 input tokens:

| Component | Tokens |
| --- | ---: |
| Image embeddings | 150 |
| Image boundary markers | 2 |
| System instruction | 89 |
| Serialized `plan` tool declaration | 96 |
| User request | 17 |
| Chat framing, including BOS | 14 |
| Total | 368 |

Method: `/apply-template`, `/tokenize`, and `/v1/chat/completions/input_tokens`. The complete request counts 368; removing the image counts 216. Two image boundary tokens leave 150 image embeddings. Independently tokenized prefix/suffix counts reconcile with the template and BOS. The PNG/base64 bytes are not text tokens. The three benchmark images have the same dimensions and preprocessing configuration; changing their scene content does not change this token count.

Normal thinking adds two prompt tokens (370 total); the brief instruction adds another 13 (383 total). These are fresh single-turn requests with no previous response history.

Measured prompt-only alternatives, not accuracy-tested:

- Shorten the user request to `Face the fridge and take one step toward it.`: save 7 tokens.
- Shorter system instruction saved in the accounting artifact: save 31 tokens.
- Remove the tool description: save 23 tokens, but lose the explicit strafe/rotate distinction.
- All three combined: 307 tokens, saving 61 (16.6%). Keep the description until accuracy is checked; system+user shortening alone would save 38.

At the quoted aggregate prefill rate of 703.81 tokens/s, 61 tokens corresponds to roughly 87 ms. This is only a scale estimate: image-encoder cost and batching/fixed overhead prevent a linear prediction. The quoted no-thinking request spends approximately 81% of its logged processing time in prefill; thinking-enabled runs instead spend most time generating reasoning. Prompt caching is another potential saving for an unchanged system/tool prefix, but must be measured with changing frames rather than identical-image replay.

## Short tool outputs

The active template/tokenizer encodes a complete `plan(actions=["forward"])` in 13 native protocol tokens. `plan(actions=["turn_left", "forward"])` needs 19. These counts include the call delimiters and tool handoff token; the HTTP response envelope is not generated by the model.

All nine thinking-off benchmark responses emitted the 13-token forward-only call. It was correct for the three centered trials and wrong for the six off-center trials. Short correct calls are the desired outcome; shortness alone says nothing about action correctness.

## Total-output cap versus reasoning budget

The installed build accepts top-level `reasoning_budget_tokens` (also `thinking_budget_tokens` as an alias), independently of `max_tokens`. `chat_template_kwargs.enable_thinking` remains the Boolean model feature. The reasoning budget is enforced by the runtime sampler using the template's thinking delimiters; it is not a native learned instruction to plan within a specific budget.

Two probes reused the saved normal-thinking right-view request, seed 302, fixed sampling, cold prompt KV:

| Settings | Generated tokens | Finish reason | Result |
| --- | ---: | --- | --- |
| `max_tokens: 64` | 64 | `length` | Only an unfinished reasoning prefix; no call |
| `reasoning_budget_tokens: 64`, `max_tokens: 128` | 88 | `tool_calls` | Complete `plan([right, right, forward])`, but wrong: strafing instead of turning |

The second response demonstrates that the budget works with this Gemma template and active MTP setup. It does not demonstrate improved accuracy. The unbounded historical request produced `turn_right, forward`, correctly; this single comparison cannot establish a general budget/quality relationship.

`max_tokens` limits reasoning plus final tool syntax together. It does not reserve space for a call or tell the model to conclude first. A reasoning budget closes the thought section and allows generation of a call using the remaining total budget. The budget resets per thinking block, and delimiter/message or UTF-8 completion tokens add overhead; it is not a global response-wide reasoning-token ceiling. Keep a separate total cap. A valid parsed call can still be semantically wrong. Treat a length-truncated response as incomplete. [Budget sampler implementation](https://github.com/ggml-org/llama.cpp/blob/a2878d30d/common/reasoning-budget.cpp#L75-L184).

Example request fields (probed, not adopted as defaults):

```json
{
  "chat_template_kwargs": {"enable_thinking": true},
  "reasoning_budget_tokens": 64,
  "max_tokens": 128
}
```

Google documents native thinking as Boolean and suggests brevity instructions; runtime enforcement is a separate control. [Google prompt formatting](https://ai.google.dev/gemma/docs/core/prompt-formatting-gemma4#tip_adaptive_thought_efficiency_using_system_instructions), [matching server request handling](https://github.com/ggml-org/llama.cpp/blob/a2878d30d/tools/server/server-common.cpp).
